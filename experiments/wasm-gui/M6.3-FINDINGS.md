# M6.3 — live shell: complete findings and fix design

## ✅ RESOLVED — the child reads its PTY stdin and echoes it back (`PTY_CHILD_REPLY_OK`)

`scripts/test-m6-3-pty.sh` now asserts the full interactive round-trip: the wasm terminal writes
`"hi"` to the PTY master, the wasm child reads it from its slave stdin (`read(0)`), and echoes
`ECHO:hi` back through the slave to the master. Bidirectional PTY I/O between two wasm guests works.

**Actual root cause (the theories below in "Last remaining gap" were WRONG — corrected here).**
The child's `read(0)` *does* reach the runner's `fd_read`, fd 0 *is* a `passthrough` handle, and the
kernel-stdin gate *is* true. It calls `__kernel_stdin_read`. The real problem was one layer below the
runner: the v8-runtime **session intercepts `_kernelStdinReadRaw` in-session**
(`crates/execution/src/javascript.rs` ~2931) as an `Immediate` result that reads a
`LocalKernelStdinBridge` — it never surfaces a host sync-RPC, so `__kernel_stdin_read` never reaches
the sidecar's kernel-fd reader (`service_javascript_kernel_stdin_sync_rpc`). That bridge is fed for a
**pipe** child by `write_descendant_javascript_child_process_stdin`; for a **pty** child the input
lives in the kernel PTY slave instead, so nothing ever fed the bridge and the child read empty forever.

Why every earlier JS-layer fix "did nothing": the diagnostic channel was the lie. The child's fd-1
writes go to the PTY slave → master, which the *parent* `pty_read`s but never forwards to the host, so
child-side traces were invisible. Forwarding the parent's master reads to fd 2 (`CHILDOUT[...]`) made
the child's `[RUNNERV74]`/`[FDREAD0 kind=passthrough smp=true kssr=true]` traces visible and pinned the
real failure to the empty in-session stdin bridge.

**The fix (sidecar-side, ~40 lines, no runner/asset change):** `pump_pty_child_stdin` in
`crates/sidecar/src/execution.rs`, called each `poll_descendant_javascript_child_process` tick. For a
child with `pty_master_fd.is_some()`, it drains the kernel PTY slave (fd 0, non-blocking) and forwards
the bytes to `child.execution.write_stdin` — feeding the same in-session bridge the pipe path feeds.
This mirrors the existing client→bridge (top-level) and parent→bridge (pipe child) pumps; the kernel
PTY is simply the input source for pty children. Guarded by the sidecar suite + M1–M7 + the M6.3 test.

Net M6.3: PTY syscall primitive + live child + **interactive stdin echo** all green. A full terminal
emulator (st/xterm) + a real wasm shell on top of this primitive remain as larger follow-on work.

# M6.3 — live shell: complete findings and fix design

The M6.3 **PTY syscall primitive is done and proven end-to-end** (`scripts/test-m6-3-pty.sh`,
host `--pty-test`): a wasm terminal guest opens a real kernel PTY via `host_net.pty_spawn`, writes the
master with `pty_write` (`__pty_write`), and reads the kernel line-discipline echo back with
`pty_read` (`__pty_read`). Stack: kernel `open_pty_split` → sidecar `configure_child_stdio` `'pty'`
stdio mode → `__pty_read`/`__pty_write` handlers → `_ptyReadRaw`/`_ptyWriteRaw` bridge bindings →
`host_net.pty_spawn`/`pty_read`/`pty_write` wasm imports.

## UPDATE: the spawned child now runs over the PTY (parent-poll drive)

`test-m6-3-pty.sh` now asserts `PTY_CHILD_RAN`: the wasm terminal spawns the wasm child over the PTY,
**drives it with the standard `child_process.poll`** (in the `pty_read` shim), and the child's `main()`
executes and its slave-stdout reaches the terminal's master. The earlier "child never runs" was
because nothing drove the nested child; the standard model (parent polls child) drives it, and a child
that reads-once-and-exits avoids the blocking-stdin deadlock. Sidecar suite + M7 desktop still green.

**Last remaining gap — EXACTLY localized:** the child's `read(0)` never reaches the kernel-stdin path
at all. In the wasm runner's `_fdRead` (wasm.rs ~3316), fd 0 resolves via
`_externalFdHandle` → `lookupFdHandle(0)` → a **synthetic `pipe-read` handle** (an empty runner-local
child_process stdin pipe; node_import_cache.rs `syntheticFdEntries`/`lookupFdHandle`). So `read(0)`
takes the `handle.kind === "pipe-read"` branch (wasm.rs:3320) — reading the empty runner pipe and
returning EOF — and NEVER reaches the `entry.kind === "stdin"` / `__kernel_stdin_read` branch
(verified: a gate log placed there never fires). Meanwhile `pty_write` puts the data on the KERNEL PTY
master → slave, a different channel. This is the classic "two-pipe mismatch" for the pty child.

**Even deeper (latest finding):** a custom `_fdRead` override is NOT the entry point for the child's
`read(0)` — instrumentation at `_fdRead` entry never fires for fd 0. The child's `read(0)` is serviced
by the underlying `node:wasi` WASI implementation's own `fd_read` (the runner only overrides some fds),
which reads whatever fd 0 was wired to at WASI preopen/stdio setup — not the kernel PTY slave. So the
fix is one layer deeper than the runner's `_fdRead`: a pty child's WASI fd 0 must be wired to read the
kernel PTY slave (via `__kernel_stdin_read`) at stdio/preopen setup, OR the runner must intercept the
WASI `fd_read` for fd 0 on a pty child and route it to the kernel slave. This is a focused
runner/WASI-stdio change (wasm.rs WASI setup + node_import_cache), regression-guarded by the sidecar
suite + M1–M7. With it, the shell reads the terminal's input and the terminal is fully interactive.

Net: the spawned shell **runs over the PTY with working stdout** today (`PTY_CHILD_RAN`); only the
stdin direction (terminal → shell) remains, localized to WASI fd-0 wiring for pty children.

### Caching caveat (important for the fix)

The actual `fd_read` import the wasm instance uses is `wasiImport.fd_read` in `NODE_WASM_RUNNER_SOURCE`
(node_import_cache.rs ~12870), wired via `new WebAssembly.Instance(module, { wasi_snapshot_preview1:
wasiImport, ... })` (~13717). For a child's fd 0, that override has a `handle.kind === 'pipe-read'`
branch (~12874) that returns EOF on a writer-less pipe, and a separate passthrough→`readKernelStdinChunk`
branch (~12938) that reads the kernel stdin. The pty child lands on the pipe-read branch.

BUT: instrumentation added to that override never fired for the child's fd 0, even with a freshly-built
guest, a bumped `NODE_IMPORT_CACHE_ASSET_VERSION`, and after confirming the snapshot cache is NOT the
cause (it is keyed by the *bridge code* digest — `snapshot.rs` `bridge_cache_key` = sha256(bridge) —
while the runner JS loads fresh per execution, so a runner-asset change DOES take effect). The prewarm
path also rebuilds from the current asset (it runs `prewarm_only` and exits before instantiation).

**The real contradiction to resolve next (confirmed by guest-side markers):** the child's `read(0)`
**blocks forever and never returns** — a marker written immediately after `read(0)` never appears on
the PTY master, while `write(1,"READY")` before it does. So the child reaches `read(0)`, it blocks, and
it does so WITHOUT calling `wasiImport.fd_read` (an entry log at the top of that override never fires,
even with a brand-new asset version and a cleared materialize cache — so it is NOT a caching issue).
Yet `fd_write` clearly uses the override (READY appears). Same instance, same import object
(`new WebAssembly.Instance(module, { wasi_snapshot_preview1: wasiImport, wasi_unstable: wasiImport })`,
then `wasi.start(instance)`).

### ROOT CAUSE FOUND (corrected & confirmed with guest-side markers)

Guest-side markers (written via fd 1, which works) prove the sequence: the child writes `READY`, then
prints `PRE_READ` (it reaches the read loop), then calls `read(0)` — and **`POST_READ` never appears:
`read(0)` blocks and never returns.** So an EARLIER conclusion in this doc ("node:wasi services fd 0
natively / the override is bypassed") was WRONG. The child's `read(0)` DOES reach `wasiImport.fd_read`
(the override); it enters the pipe-read branch (fd 0's synthetic child_process pipe has a *write end*
but stays empty, since the terminal writes the kernel PTY master) and **blocks forever** in that loop.

Routing fd-0 to `readKernelStdinChunk` (the kernel slave) ALSO blocks, and the reliable kernel-side
`__kernel_stdin_read` log never fires — because the child's blocking stdin **sync-RPC is never serviced
by the parent's `child_process.poll`**. `__kernel_stdio_write` (READY) WAS serviced because it returns
immediately in a single poll; a *blocking* stdin read loop's sync-RPCs are not pumped while the child
sits blocked. This is the SAME core blocker as the historical section below: **child sync-RPC servicing
concurrency** — a spawned child's blocking host-calls are not driven concurrently with a live parent.

**THE FIX is the child-execution / sync-RPC servicing concurrency change** (see "Fix options" below),
NOT a node:wasi or override-layer change. Once a spawned child's blocking sync-RPCs are serviced
concurrently (e.g. the child runs as a top-level-serviced execution, or the parent's poll pumps the
child's stdin RPCs to completion), routing fd-0 reads to `readKernelStdinChunk` (kernel slave) makes the
shell read the terminal's input. Everything else is proven: kernel slave, `open_pty_split`,
`__pty_read`/`__pty_write`, child spawn, and stdout over the PTY (`PTY_CHILD_RAN`).

### Refinement: the child blocks in `poll_oneoff`, not `fd_read`

wasi-libc's blocking `read(0)` first calls `poll_oneoff` to wait for fd-0 readability, THEN `fd_read`.
The child blocks in `poll_oneoff` (node_import_cache.rs `wasiImport.poll_oneoff` ~13460) — `fd_read` is
never reached, which is why all the `fd_read`-layer fixes had no effect. `poll_oneoff` only routes an
fd-0 subscription to the kernel (`collectKernelReadyEvents` → `__kernel_poll` on the slave) when fd 0's
handle is a `passthrough` AND `(sidecarManagedProcess || KERNEL_STDIO_SYNC_RPC)` (lines 13488-13495,
13526-13527). The child's fd 0 does NOT satisfy that (it is a synthetic child_process `pipe-read`, or a
passthrough whose sidecar gate is false), so `poll_oneoff` falls to the synthetic/native poll on fd 0,
which never becomes readable → permanent block, before `fd_read`.

**Precise fix:** make the spawned child's fd 0 kernel-backed in BOTH `poll_oneoff` AND `fd_read` — the
cleanest form is to give a pty/sidecar child a `passthrough` fd-0 handle (targetFd 0) with the sidecar
gate true, so the EXISTING passthrough+fd0 kernel paths (`poll_oneoff` 13492, `collectKernelReadyEvents`
13526, `fd_read` 12938 → `readKernelStdinChunk`) handle it without new poll logic. This is delicate
(poll_oneoff is on the hot path for every guest — X server/clients/M5-M7 all depend on it), so it must
be done deliberately with the full sidecar suite + M1-M7 desktop as the regression guard.

### Confirmed: the child does NOT take the kernel-poll path for fd 0

A kernel-side log in `kernel.rs poll_fds` for fd 0 never fired for the child — so `poll_oneoff` does not
route fd-0 to `__kernel_poll`. That requires fd 0 to be a `passthrough` handle AND the sidecar gate
true. The gate (`process.env.AGENT_OS_SANDBOX_ROOT` / `KERNEL_STDIO_SYNC_RPC` =
`process.env.AGENT_OS_WASI_STDIO_SYNC_RPC`) reads `process.env`, where `AGENT_OS_*` is scrubbed. Note
`__agentOsWasmInternalEnv` (the unscrubbed copy) is NOT in scope in `NODE_WASM_RUNNER_SOURCE`
(node_import_cache) — only in the wasm.rs bootstrap — so a gate fix there can't simply read it.

**Observability limitation for the next session:** JS-side logs in the runner are LOST when the child
blocks (stderr isn't flushed), so debugging must use kernel-side `eprintln` (reliable) — instrument the
child's fd-0 handle kind and the gate value by having the bootstrap stamp them somewhere the kernel can
read, or log from `poll_targets`/`fd_read` in the kernel. The fix likely needs the wasm.rs bootstrap to
expose the gate (e.g. `globalThis.__agentOsKernelStdio = true`, computed from the internal env) so both
`poll_oneoff` and `fd_read` in node_import_cache can consult it, AND to ensure the child's fd 0 is a
passthrough handle. This is the universal wasm-guest-stdin gap (not pty-specific) and is the single
remaining blocker for an interactive shell; stdout, child execution, and the PTY primitive are proven.

## (historical) The original blocker: a spawned child's execution never ran

A real terminal runs a real shell, and a real shell spawns child processes (the commands). Both the
shell-under-the-terminal and the commands-under-the-shell are spawned guests. **Spawned child guest
executions do not run concurrently with a busy parent**, which blocks the entire live-terminal path.

### What was proven by instrumentation (not guessed)

- `child_process.spawn` of a wasm child succeeds and returns a working `ptyMasterFd`; the PTY I/O
  round-trips (via the kernel line discipline).
- The spawned child's `main()` never executes (a `write()` placed before any `read()` never appears).
- Promoting the child to a **top-level** process so the main async pump loop drives it: the child
  IS iterated and polled by the main loop (confirmed 353×, `process_ids = ["proc-pty",
  "proc-pty/child-1"]`), but `execution.poll_event()` returns `None` **every time** — the child
  session emits zero events, not even its bootstrap host-calls.
- Each execution gets its own OS thread (`v8-runtime/src/session.rs` `create_session` →
  `thread::Builder::spawn`), so the child session thread exists; it is blocked before producing any
  event. Its bootstrap host-calls are not being serviced/answered, so its thread never advances.
- A blocking parent poll (`child_process.poll`) to drive the child instead deadlocks: the child's own
  sync-RPCs need the single sidecar service thread that the blocking poll holds.

### Root cause (precisely localized via instrumentation)

The child's V8 **session does run** — instrumenting `session_thread` (v8-runtime/src/session.rs) shows
every spawned child session acquires a concurrency slot (default = CPU count, not the limit here) and
receives + runs its `Execute` command. So the child is not unstarted or slot-starved.

The break is in **event routing**: the child session emits its events/host-calls onto a channel bound
to its **creation-time parent context**, not onto the channel that the (promoted) child's own
`ActiveProcess.execution.poll_event()` reads. Instrumenting the main async pump loop confirms it
iterates and polls the promoted top-level child 353× but `poll_event` returns `None` every time — the
child's bootstrap host-call never surfaces there. So nothing services the child's first host-call, the
child session blocks on it forever, and the child produces no output. Merely moving the child's
`ActiveProcess` to the top level does NOT rebind the session→execution event routing.

**Exact fix location:** the embedded-runtime session→execution event routing (the `event_tx` /
`call_id_router` path in `v8-runtime/src/session.rs` and how `execution.poll_event` is wired to a
session id at spawn). A spawned child needs its session's events routed to a channel that a top-level
pump can poll AND its host-calls serviced in the *child's own* kernel context (its own `kernel_pid`,
so `__kernel_stdin_read` on fd 0 hits the child's PTY slave, not the parent's). This is the highest-
risk core component (every guest's process spawning depends on it) and must be changed deliberately
with the full sidecar suite + M1–M7 desktop as the regression guard.

## Fix options (each a deliberate, separately-reviewed change — NOT trial-and-error)

1. **Concurrent child-session servicing (core-runtime).** Make a spawned child's host-calls serviced
   independently of the parent's poll — e.g. give PTY/long-lived children a top-level servicing
   identity at spawn so the main async pump loop both polls AND services their sync-RPCs. Blast radius:
   the whole `child_process` subsystem; must be guarded by the full sidecar suite + M1–M7 desktop.
2. **Launch the shell as a top-level guest with a host-wired PTY (avoids child_process).** Add a
   `pty` stdio mode to the top-level `execute` path: the sidecar opens a PTY for the new guest, dups
   the slave onto its 0/1/2, and exposes the master fd over the wire. The host (which already drives
   input via XTEST and reads the framebuffer) drives the shell's PTY master. This uses the proven
   top-level concurrent-execution model (X server + clients, M5) and sidesteps the child-session
   blocker. Caveat: a real shell still needs to spawn command children, which re-hits option 1 unless
   the shell is builtin-only.

The PTY syscall plumbing (this milestone's novel part) is complete and reusable by either option.

## FINAL CONFIRMED ROOT CAUSE (supersedes the poll_oneoff theory above)

After implementing the FULL fix (route fd-0 to the kernel in BOTH `poll_oneoff` — a new `kernelStdin`
subscription path — AND `fd_read`), the reliable kernel-side logs `[pty-kpoll]` (kernel `poll_fds` for
fd 0) and `[pty-stdin]` (`__kernel_stdin_read` service) STILL never fired, and the child's `read(0)`
still blocked. Confirmed earlier facts: the child reaches `read(0)` (`PRE_READ`) and it never returns
(no `POST_READ`); the child's env DOES carry `AGENT_OS_SANDBOX_ROOT` + `AGENT_OS_WASI_STDIO_SYNC_RPC`
(so the gate is satisfiable); fd-1 WRITE reaches the kernel (stdout/`PTY_CHILD_RAN` works).

Therefore: the child's fd-0 READ is serviced by **node:wasi natively in Node core**, below the JS WASI
import layer — no JS-layer override (`fd_read`, `fd_pread`, `poll_oneoff`, top-of-function routes) is
ever consulted for fd 0 read, while fd-1 WRITE IS consulted. The poll_oneoff "blocks in the synthetic
pipe" theory was based on an unverified assumption (that wasi-libc polls before reading) and is
incorrect; the read blocks in node:wasi's native stdin handling.

**THE FIX must be at the node:wasi / Node-core level (not the JS import overrides):** stop node:wasi
from binding fd 0 as a native standard stream so the guest's `fd_read(0)` falls through to the JS WASI
import, OR bridge node:wasi's stdin host fd to the kernel PTY slave, OR replace node:wasi with a custom
WASI implementation for sidecar guests whose `fd_read`/`poll_oneoff` ARE honored for fd 0. This is the
universal wasm-guest-stdin gap (affects every wasm guest, not just pty children). Everything below it is
proven: kernel `open_pty_split`, `__pty_read`/`__pty_write`, child spawn over the PTY, and stdout over
the PTY (`PTY_CHILD_RAN`). The interactive shell needs this node:wasi-level fix, then a terminal
emulator (st/xterm) and a wasm shell on top.

## DEFINITIVE PROOF (reliable, sidecar-side): node:wasi services fd-0 read natively

A log placed in the sidecar's `poll_descendant_javascript_child_process` (reliable — it runs in the
sidecar, not the blocked child) recorded EVERY event the child emits when the terminal polls it:

    [pty-childev] child=child-1 event=SyncRpc(__kernel_stdio_write)   # the READY write (fd 1)
    [pty-childev] child=child-1 event=Stdout(READY)
    (… then nothing — the child blocks in read(0) and emits no further events …)

The child emits `__kernel_stdio_write` for its fd-1 WRITE (so the JS `wasiImport.fd_write` override IS
used and routes to the kernel slave → stdout works), but it **NEVER emits `__kernel_stdin_read`** for
its fd-0 READ. So `read(0)` makes no kernel sync-RPC whatsoever — it is serviced entirely inside
node:wasi's native (Node core) stdin handling, reading the host runner's fd 0, which never receives the
terminal's input (that goes to the kernel PTY master). This DEFINITIVELY settles the earlier
back-and-forth: the fd-0 READ path does not reach any JS `wasiImport`/runner override, so no override-
or kernel-routing fix can work. The fd-1 WRITE / fd-0 READ asymmetry is node:wasi's: it routes writes
through the JS import but services blocking stdin reads natively.

**THE FIX (node:wasi / WASI-construction level):** the runner builds `new WASI({...})` without a
`stdin` option, so node:wasi binds fd 0 to native host stdin. To make a sidecar guest's `read(0)` reach
the kernel PTY slave, the runner must either (a) construct the WASI so fd 0 is NOT a native standard
stream (so `fd_read(0)` dispatches to the JS `wasiImport.fd_read` override, which then routes to
`readKernelStdinChunk`), or (b) give node:wasi a `stdin` host fd that is bridged to the kernel slave, or
(c) replace node:wasi with a custom WASI implementation for sidecar guests. This is the universal wasm-
guest-stdin gap (every wasm guest, not just pty children). Everything else is proven: `open_pty_split`,
`__pty_read`/`__pty_write`, child spawn over the PTY, and stdout over the PTY (`PTY_CHILD_RAN`). On top
of this fix, M6.3 still needs a real terminal emulator (st/xterm) and a wasm shell.

### Also tried (and failed): bootstrap-exposed global gate

Hypothesis: the fd-0 kernel routes' gate read `process.env` (AGENT_OS_* scrubbed) so it was false.
Fix attempt: the wasm.rs bootstrap set `globalThis.__agentOsKernelStdioEnabled` from the UNSCRUBBED
`__agentOsWasmInternalEnv`, and `poll_oneoff` + `fd_read` (a new `kernelStdin` poll path + a top-of-
function fd-0 read route) consulted that global. Result: STILL no `__kernel_stdin_read` / `__kernel_poll`
emitted by the child (reliable sidecar `poll_descendant` log shows only `__kernel_stdio_write`). This
CONFIRMS that node:wasi never calls the JS `wasiImport.fd_read` / `poll_oneoff` for fd 0 at all — the
gate was never the issue; node:wasi services fd-0 read entirely in Node-core, below the JS WASI imports.

**Conclusion:** no JS-layer change (gate, override route, poll route, bootstrap global) can fix fd-0
read, because node:wasi does not dispatch fd-0 read to the JS imports. The fix REQUIRES replacing
node:wasi's stdin handling for sidecar guests — e.g. a custom WASI `fd_read`/`poll_oneoff` for fd 0 that
the guest actually invokes (not node:wasi's native path), or constructing the WASI so fd 0 is a normal
preopen routed through the import. That is a node:wasi-integration change of real scope, to be done
deliberately. (fd-1/2 WRITE already go through the JS import — only fd-0 READ is native.)

## Most decisive test: ungated fd-0 route at the TOP of the instance's fd_read

Final disambiguation: placed an UNGATED route at the very top of `wasiImport.fd_read` (the function
bound as the instance's `wasi_snapshot_preview1.fd_read` at `new WebAssembly.Instance(...)`): for fd 0,
unconditionally call `readKernelStdinChunk` (which would emit `__kernel_stdin_read`). Reliable sidecar
log: the child STILL emits only `__kernel_stdio_write` (its fd-1 write) and NEVER `__kernel_stdin_read`.

So the child's `read(0)` does not invoke the bound `wasiImport.fd_read` at all, even though (a) the
guest imports `fd_read` from `wasi_snapshot_preview1` (confirmed via wasm-objdump), (b) the instance is
created with `{ wasi_snapshot_preview1: wasiImport }`, (c) `wasiImport.fd_read` is that override, and
(d) the guest's fd-1 WRITE DOES reach `wasiImport`'s write path. This is an irreducible contradiction
under the obvious model of wasm imports — `read(0)` is invoked (PRE_READ marker) and blocks (no
POST_READ), yet the bound fd_read override is bypassed while fd_write is honored.

The resolution lies in how the WASI *polyfill* (`globalThis.__agentOsWasiModule`, defined in
`crates/execution/src/wasm.rs`) instantiates and starts the module (`wasi.start(instance)`) and how its
own fd-0 stdin handling interacts with the runner's `wasiImport` override — knowledge of that embedding
is needed to fix it. The next debugging step requires reliable tracing INSIDE the polyfill's
start()/fd-0 path (e.g. writing to a kernel-readable file from the polyfill, since the child's own
stderr is lost when it blocks). This is maintainer-level runtime work; everything below it (kernel PTY
slave, `__pty_read`/`__pty_write`, child spawn, stdout over the PTY) is proven.
