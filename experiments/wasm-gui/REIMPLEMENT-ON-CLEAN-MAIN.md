## 1. TL;DR verdict — RE-IMPLEMENT, do not rebase

A git/jj rebase is **not viable**. Since the fork, main did two structural things that collide with every wasmgui hot file:

1. **The kernel→vfs split.** The entire VFS was extracted out of `crates/kernel` into a **new `crates/vfs` crate**. Main deleted `kernel/src/{vfs,overlay_fs,root_fs,mount_table,mount_plugin}.rs` and recreated them under `crates/vfs/src/posix/`, added a storage-engine layer (`crates/vfs/src/engine/*`), and added `crates/secure-exec-vfs` with S3 backends. S3 plugins were rewritten (`s3.rs` → `s3_common.rs` + `object_s3.rs` + chunked); `sqlite_vfs` removed.
2. **Hot-file rewrites.** The exact files wasmgui edits most were independently heavily rewritten on main: `sidecar/src/execution.rs`, `sidecar/src/service.rs`, `sidecar/src/stdio.rs`, `execution/src/node_import_cache.rs`, `execution/src/wasm.rs`, `execution/src/javascript.rs`, `v8-runtime/src/{session.rs,bridge.rs}`, `kernel/src/kernel.rs`, `snapshot.rs`.

So cross-crate file moves + colliding rewrites mean **port by behavior, not by patch**. For every keeper below, the note says which **new** crate/module it lands in and what it must be re-seated against.

**What stayed in `crates/kernel` (NOT moved to vfs):** fd-table, pipes, ptys, poll/PollNotifier, process-table, socket-table, resource accounting. So the inline-poll handle, kernel-pipe surface, PTY primitive, wasm-thread process model, and procfs all still land in `crates/kernel`. **What moved to `crates/vfs`:** file backends, overlay/root FS, mount table — so `pwrite` forwarding, char-device synthesis, `MemoryFileSystem` in-place writes, and path-open probes re-seat there.

**Rough scorecard across all 12 areas:**

| Verdict | Count (approx) | What it means |
|---|---|---|
| **KEEP** (live, port it) | ~38 | Landed/wired behavior worth re-implementing |
| **KEEP-AS-DESIGN** (docs/specs/reviewed-but-unbuilt) | ~17 | Carry forward as the roadmap & reviewed reference |
| **DROP** (dead / refuted / throwaway) | ~10 | Do not re-implement (some keep a reviewed reference file) |
| **MAYBE** (measure first) | ~7 | Re-validate before committing |

**The single most load-bearing finding:** the inline-dispatch family is the **only parallelism that landed and is default-ON** (~32% input-latency win). The fuller Root-2 service-thread multiplex is **design-only** and was strategically **re-scoped** (the service thread is ~99% idle; the real bottleneck is cross-thread wake latency, so multiplexing that thread does *not* help — co-location is the surviving direction). Also note a **doc landmine**: `PERF-OPTIMIZATION.md:423` still says "THE INLINE-DISPATCH FAMILY IS REFUTED" — that verdict was **reversed**; the code ships default-on.

### 2a. Core runtime architecture

#### K1. Inline dispatch + KernelPollHandle (the landed per-session parallelism) ★ headline
*Reconciled from: area "Inline dispatch" (6 sub-changes), "WASI syscall surface" #7, "T1 SAB" context, "Perf findings" inline-dispatch entry. These are ONE feature.*

- **What:** Each guest already has a per-session V8/WASM event-bridge thread. This lets that thread service the three hottest **non-blocking** sync-RPCs — unix `net.poll` (lever A), `__kernel_fd_poll` (lever C-lite, the dominant ~9000/run X-loop hop), and `net.server_accept` "nothing pending" (lever T-accept, ~4400/run) — **inline, off the single shared sidecar service loop ("the funnel")**, concurrently per guest. Anything not provably inline-equivalent falls through to the funnel unchanged.
- **Why keep:** ~32% input-latency win (~105ms→~71ms / ~64ms on the trustworthy glyph metric), render green, no CPU spin. The **only** landed parallelism. Default-ON.
- **Components (all must land together):**

A `#[derive(Clone)]` read-only handle (Arc-clones of FdTableManager/PipeManager/PtyManager/PollNotifier/driver_pids). Bounded event-driven park on the existing `PollNotifier` (`crates/kernel/src/poll.rs:133/137`, **0 diff vs fork — reuse as-is**).
  - **InlineNetDrain trait + bridge interception** — `crates/execution/src/javascript.rs:456-506` (trait), `:531-556` (`LocalBridgeState.net_drain`), `:2877-2989` (three interception blocks in `spawn_v8_event_bridge` for `_netSocketPollRaw` wait==0 only / `_kernelFdPollRaw` / `_netServerAcceptRaw`), `:1813-1821`/`:1956-1961` (plumbing). #### K2. WASM threading (wasi-threads runtime) ★
*Reconciled from: area "WASM threading" (7 sub-changes), "WASI syscall surface" #1 (`wasm.thread_spawn`), "Linux-support ledger" §F. ONE feature.*

- **What:** A multi-threaded WASM guest runs as N V8 isolates on N OS threads sharing ONE linear memory (imported SAB-backed `WebAssembly.Memory`). Production path: guest `pthread_create` → runner registers a thread-start token + shares memory → sidecar `wasm.thread_spawn` spawns a **worker wasm session** reusing the parent's `kernel_pid` + fd-table (real kernel host calls, GTK/GLib path), entering at `wasi_thread_start`. Bare-isolate direct-spawn fallback (stub WASI, compute-only) also exists.

- **generic-vs-gui:** generic-runtime (mixed for the sidecar worker model).
- **Reimpl notes:**
  - **Crate map:** `wasm_threads.rs` lands unchanged in `crates/v8-runtime` (**not vfs-moved**). ## 4. CARRY-AS-DESIGN — unbuilt-but-proven-needed

These are docs/specs to port verbatim as the roadmap. Re-anchor every cited file:line against main (hot-file rewrites + vfs split moved them all).

#### D1. Root-2 multiplex + the corrected strategy ★ most load-bearing design finding
- **The wall:** every guest's syscalls AND the X/D-Bus servers funnel through ONE single-threaded sidecar service loop (`&mut sidecar` at `stdio.rs:193-279`). `ROOT-2-MULTIPLEX-DESIGN.md` frames four kernel-concurrency options (A global mutex — rejected; B per-subsystem locks; C per-guest sharding; D dedicated X-IO thread).
- **THE CORRECTION (`XU7-SIMULTANEITY-NEXT-STEPS.md`, settled by measurement):** option A/D do **NOT** help — the sync-RPC service thread is **~99% idle** (proved by RPCPROF, `wasm.rs:1023-1030`); the bottleneck is per-round-trip cross-thread **wake latency** (~180µs × hundreds of thousands of X/D-Bus round-trips) through single-threaded service guests. Path C (adaptive spin-poll) was **built, tested, REFUTED** (multi-app got worse). **Path B (co-location** — Xvfb+clients+daemons in one isolate, short-circuit loopback X/D-Bus to in-process calls) is the only un-refuted direction, but needs Asyncify or fibers + a cooperative scheduler (unsolved).
- **Carry-forward rule:** do NOT invest in the service-thread multiplex/lock refactor until co-location is evaluated. **On main the lock surface CHANGED** — main's vfs extraction already split some kernel subsystems out, so the per-subsystem locking B needs may be partially done or differently shaped (engine/posix layers). Re-survey which subsystems `crates/kernel` still owns vs `crates/vfs` before designing lock granularity. #### D2. Root-1 selective-fpcast binaryen pass (the GObject compute floor)

#### D3. Other unbuilt levers (measure before committing — MAYBE)
- **Reader-carry (F3-DEFERRED):** off-thread socket reader carries drained bytes INTO the poll_wait completion (removes ~half the hops).

#### D5. The M8 FFI keystone (libffi-wasm) — proven possible, must re-seat

Prereq for every GTK milestone — this is really part of K2/K3 but tracked here as the keystone discovery.
