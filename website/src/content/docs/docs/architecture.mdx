Secure Exec runs untrusted guest code inside a fully virtualized VM. Nothing the guest does touches the host directly: every guest syscall is serviced by a kernel that Secure Exec owns.

## The three components

- **Client**: trusted. Your process imports `NodeRuntime` (or uses the Rust client), supplies config, policy, and limits, and submits the untrusted payload to run.
- **Sidecar**: trusted, and the enforcement point. It owns the kernel, the virtual filesystem, the process and socket tables, the permission policy, and the language runtimes that execute guest code.
- **Executor**: untrusted. Guest JavaScript (V8 isolates) and WASM run here, holding no real capabilities of their own.

## Kernel-owned syscalls

- **Everything is virtualized**: there is no real host filesystem, host network socket, or host process available to the guest.
- **Every guest syscall flows through the kernel**: filesystem, processes, sockets, pipes, PTYs, and DNS are all serviced by kernel-owned paths inside the sidecar.
- **The security boundary is sidecar to executor**: the policy and limits are enforced on every scope, so the executor cannot reach a capability the policy denies. See the [Security Model](/docs/security-model) for the in-scope and out-of-scope threat model.
